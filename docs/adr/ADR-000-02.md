# ADR-000-02 — Backend en Java + Spring Boot

**Estado:** Aceptado — documentado retroactivamente el 2026-09-21 (decisión ya tomada en el código, recién formalizada)

## Contexto
La Constitución (Registro de Decisiones Técnicas) marca el backend como "Decidido, evaluado
contra Go y Node.js" desde el inicio del proyecto, pero esa evaluación nunca quedó escrita en
ningún ADR. Es la decisión tecnológica más visible del trabajo — todo lo demás (los 9 módulos,
Quartz, JPA, Spring Security) se apoya en ella — y la auditoría independiente la señala como la
única sin respaldo documental (informe §7.2, pregunta 8). Un jurado de tesis va a preguntar por
qué Java y no algo "más liviano"; la respuesta tiene que estar escrita antes de esa pregunta, no
improvisada en la defensa.

El criterio del Artículo VII es explícito: toda decisión técnica se justifica **contra el tamaño
real del equipo y el presupuesto** — 1 desarrollador, USD 0-100/mes durante el desarrollo — no
contra "buena práctica" genérica de una empresa de otra escala. Este ADR aplica ese criterio.

## Decisión
Backend monolítico en **Java 21 + Spring Boot**, con Quartz (JobStore JDBC), JPA/Hibernate +
Flyway, y Spring Security como los cuatro pilares de infraestructura que la elección de lenguaje
trae resueltos de fábrica.

Los ejes que pesaron, en orden de peso real para un proyecto de 1 desarrollador:

1. **Quartz con JobStore JDBC persistido, contra el Artículo X.** El Artículo X prohíbe cualquier
   timeout de negocio (escrow, kill-switch, cancelaciones, reactivación de sanciones) en memoria
   volátil. Java tiene en Quartz un scheduler persistido, maduro (desde 2001), con `driverDelegateClass`
   probado contra PostgreSQL y documentación operativa extensa — `QuartzPersistenciaTest` en este
   repo lo verifica contra un reinicio real. La comparación honesta **no es que Go y Node carezcan
   de opción** — la tienen, y hay que nombrarla para que el argumento no se caiga con un solo
   contraejemplo: Node tiene `pg-boss` y `graphile-worker`, ambos schedulers persistidos nativos de
   PostgreSQL con soporte de cron, sin forzar un segundo motor de datos; Go tiene `river` y
   `asynq`, con persistencia y semántica de reintentos comparable. Se evaluaron y se descartaron,
   no por inexistencia sino por tres razones concretas: (a) ninguno tiene la trayectoria operativa
   de Quartz — Quartz lleva usándose en producción desde 2001, con dos décadas de casos borde de
   `misfire`/recovery ya resueltos y documentados, mientras que `pg-boss`/`river` son de la última
   década y tienen comunidades más chicas para resolver un problema operativo a las 3 AM; (b)
   ninguno se integra de fábrica con el resto de la pila elegida en este mismo ADR (Spring
   Security, JPA/Hibernate, Flyway) — habría que coser Quartz-equivalente + JPA + auth en un
   ecosistema distinto igual, perdiendo la ventaja de "todo en el mismo framework" que es el punto
   central de esta decisión; (c) familiaridad del único desarrollador (punto 5) con el ecosistema
   Spring/Quartz por sobre empezar de cero en Go o Node para este componente específico. Ninguna de
   las tres razones es "no existe" — las tres son de costo de adopción contra el Artículo VII.

2. **JPA/Hibernate + Flyway + `ddl-auto: validate` para 23 migraciones y 9 schemas.** El proyecto
   tiene 9 schemas de dominio (Artículo VIII) con relaciones cruzadas complejas (FKs entre
   `identidad`, `reservas`, `pagos`, `aula`...). Flyway con `ddl-auto: validate` (nunca `update`)
   da control de versión explícito del esquema y un chequeo de arranque que falla rápido si el
   código y la base divergen — crítico cuando el único desarrollador es también el único QA. El
   equivalente en Go (`sqlc`, `ent`, migraciones a mano con `golang-migrate`) exige escribir SQL
   explícito para cada query, más trabajo por feature con el mismo presupuesto de tiempo. En Node,
   Prisma es comparable a JPA en ergonomía, pero su generación de tipos y su motor de migraciones
   tienen menos trayectoria en escenarios de 9 schemas con FKs cruzadas que Flyway+Hibernate,
   que son el combo de facto en proyectos JVM de este tamaño desde hace más de una década.

3. **Spring Security para el NFR-SEC-02 sin escribir auth propia.** El NFR de seguridad exige TLS
   1.2+, hashing bcrypt/argon2 y log de auditoría de toda acción de Admin. Spring Security da
   filtros de autenticación/autorización, integración con JWT y hashing de contraseñas
   configurables sin escribir el pipeline desde cero. Go y Node no tienen un framework de
   seguridad de esa cobertura como estándar del ecosistema — cada proyecto arma su propia
   composición de librerías (`passport.js`, middlewares sueltos). Para 1 desarrollador, "no
   inventar autenticación" es la lectura correcta del Artículo VII, no una preferencia.

4. **La transacción del publicador compartida con los listeners de `ApplicationEventPublisher`.**
   El Artículo IX exige eventos de dominio en memoria para efectos secundarios de un solo disparo
   con múltiples reacciones, sin message broker externo. En Spring, los listeners de
   `ApplicationEventPublisher` (por defecto, síncronos) corren **dentro de la misma transacción**
   que el publicador — ver `SancionListeners` y `Plan_M9 §2.5`: si el listener de M4 (cancelar
   reservas futuras) falla, la sanción de M1 tampoco se persiste. Eso da atomicidad real entre
   3-4 efectos secundarios de una sanción **sin saga ni compensación**, con el motor transaccional
   estándar del framework. Replicar esa garantía en Go o Node exige coser manualmente una
   transacción de base de datos alrededor de una cola de callbacks — trabajo de infraestructura
   que Spring resuelve por convención.

5. **Familiaridad del único desarrollador.** Bajo el Artículo VII, esto es un criterio legítimo,
   no una excusa: con 1 desarrollador y sin equipo que amortigüe una curva de aprendizaje, elegir
   el stack en el que se es productivo día uno reduce directamente el riesgo de entrega — el mismo
   riesgo que el Artículo XI pide mitigar antes que la velocidad de feature.

## Alternativas descartadas
- **Go, con `river`/`asynq` como scheduler persistido:** rendimiento y footprint superiores, y la
  falta de scheduler persistido **no es el argumento** (existe, ver punto 1). Se descartó porque
  Go no tiene un framework de seguridad estándar del ecosistema equivalente a Spring Security
  (punto 3) — habría significado construir esa pieza a mano — y porque el desarrollador único no
  tenía la misma familiaridad de partida con Go que con la pila Spring (punto 5), lo que bajo el
  Artículo XI (mitigar riesgo de entrega) pesa más que el rendimiento. El proyecto no tiene, además,
  un requisito de throughput medido que Go resuelva y Java no.
- **Node.js/TypeScript, con `pg-boss`/`graphile-worker` como scheduler persistido sobre
  PostgreSQL:** mismo lenguaje en todo el stack (frontend ya es Next.js/React), ventaja real de
  contexto compartido, y el argumento "no hay equivalente a Quartz+JDBC" tampoco aplica acá sin
  matiz — `pg-boss` cumple el requisito de persistencia sin forzar un segundo motor de datos. Se
  descartó por trayectoria operativa (Quartz lleva dos décadas más de casos de producción
  resueltos) y porque el ecosistema de ORMs maduros para 9 schemas con FKs cruzadas (Prisma
  incluido) es más joven que Hibernate en ese escenario concreto. Es la alternativa más fuerte de
  las dos — la ventaja de lenguaje único con el frontend es real — pero no alcanza para superar la
  ventaja combinada de Quartz+JPA+Spring Security integrados de fábrica.

## Riesgo aceptado
Ninguno nuevo: esta es la decisión de base sobre la que se construyó todo el sistema, no una
concesión. El riesgo que sí se acepta explícitamente es de **stack único**: con 1 desarrollador,
si esa persona no puede seguir en el proyecto, el conocimiento operativo de Quartz/JPA/Spring
Security no está distribuido en un equipo. Es el mismo riesgo de cualquier proyecto de 1
desarrollador, no específico de esta elección de lenguaje.

## Consecuencia honesta: la excepción al Artículo VIII
El ecosistema de `sentence-transformers` (embeddings semánticos para el motor de matching de M2)
**no existe en Java** con la madurez, el catálogo de modelos pre-entrenados en español y la
comunidad activa que tiene en Python. Java tiene bindings de ONNX Runtime y proyectos como DJL,
pero ninguno reproduce la ergonomía de `sentence-transformers` + FAISS para un desarrollador
solo, en el tiempo disponible. Esto forzó la **única excepción al Artículo VIII** (que prohíbe
microservicios propios adicionales): `matching-service`, un proceso Python separado, sin lógica
de negocio propia (`MatchingOrquestador` en el monolito la retiene), documentado como excepción
explícita en el propio Artículo VIII y evaluado en la auditoría (informe §7.2, pregunta 9) como
"bien resuelto". Se declara acá sin eufemismo: la elección de Java para el resto del sistema es
precisamente lo que hizo necesaria esa excepción — no es una consecuencia separada, es el costo
directo de esta decisión.

La mitad incómoda de esa misma pregunta 9, que no se puede omitir citando solo el "bien resuelto":
el informe agrega textualmente *"Punto débil a anticipar: el servicio **escribe** en la base
compartida (AUD-015)"*. AUD-015 es más específico todavía — `matching-service` no tiene ninguna
autenticación sobre sus endpoints, y `docker-compose` lo publica en el puerto 8000 del host, con
escritura directa a la base de datos compartida con el backend Java. Es una excepción al Artículo
VIII que además tiene, hoy, una superficie de ataque propia. **No está mitigado por este ADR** —
la mitigación es Task 2.4 de FASE 2 del plan de remediación (autenticación + pooling de conexiones
en `matching-service`, AUD-015), fuera del alcance de esta tarea. Se declara acá para que la
defensa de esta decisión no se apoye en una lectura parcial del propio informe de auditoría.

## Implementación
Ya aplicada desde el inicio del proyecto: `backend/` completo (Spring Boot 3.3.4, Java 21),
`backend/src/main/resources/application.yml` (Quartz JobStore JDBC, Flyway, JWT vía Spring
Security), `matching-service/` (Python, la excepción). Este ADR no agrega código nuevo — formaliza
la elección ya deployada en `main`.

## Consecuencias
- Toda pieza de infraestructura transversal futura (nuevo scheduler, nueva integración de
  seguridad) hereda el ecosistema Spring por defecto — desviarse requiere ADR propio (AGENTS.md §2).
- La excepción de `matching-service` no autoriza nuevas excepciones al Artículo VIII: cualquier
  otro módulo que "necesite" un proceso separado requiere su propio ADR con una justificación de
  ecosistema tan concreta como la de `sentence-transformers`, no una preferencia de estilo.
- Actualizar Spring Boot 3.3.4 es deuda barata y sin bloqueo (informe §8.3) — no lo resuelve este
  ADR, queda como tarea de mantenimiento.
