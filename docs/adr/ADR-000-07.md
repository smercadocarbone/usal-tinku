# ADR-000-07 — Producción: todo en un VPS con Coolify, imágenes desde GitHub Actions

**Estado:** Aceptado — 2026-09-24 (decisión del usuario). **Enmienda** la topología de
`docs/superpowers/specs/tesis/T13-despliegue-produccion.md` §1 y §6 (Supabase + Vercel).

## Contexto

T13 repartía producción en tres proveedores: backend y matching en un VPS con Coolify, Postgres en
Supabase y el frontend en Vercel. El usuario ya tiene un VPS de **8 GB** con Coolify andando y pidió
"todos los servicios en Coolify". Restricciones del Artículo VII: 1 desarrollador, USD 0-100/mes.

Se evaluó además desplegar con un runner de GitHub Actions dentro del VPS (sin Coolify): se descartó
porque el runner ejecutaría código del repo con acceso a la máquina de producción (base y secretos),
compilar las imágenes en el VPS le saca RAM a la app, y HTTPS, dominios, vuelta atrás y backups
quedarían en scripts propios.

## Decisión

1. **Un VPS, cuatro contenedores** en un recurso "Docker Compose" de Coolify
   (`deploy/docker-compose.coolify.yml`): `db` (pgvector/pg16, volumen propio), `matching`, `backend`,
   `frontend`. Ningún servicio publica puertos (T13 TD2).
   **Entrada por Cloudflare Tunnel** (actualización 2026-09-24): el "VPS" es un servidor en la casa
   del usuario, sin IP fija. Un contenedor `cloudflared` en el mismo compose abre el túnel hacia
   Cloudflare, que enruta `tinku.site` → `frontend:3000` y `api.tinku.site` → `backend:8080`. HTTPS lo
   pone Cloudflare; Coolify no maneja dominios ni certificados y no se abre ningún puerto en el router.
   Como todo llega desde cloudflared, el rate limiting toma la IP real de `CF-Connecting-IP`
   (`RATE_LIMIT_HEADER_IP`), seguro porque el backend no es alcanzable por otro camino.
2. **Las imágenes se construyen en GitHub Actions, nunca en el VPS** (`.github/workflows/deploy.yml`):
   en cada push a `main` corren las suites de backend, frontend y matching; si pasan, se publican en
   GHCR con el hash del commit y `latest`, y el workflow llama al webhook de deploy de Coolify.
3. **Sin rama `develop` ni staging por ahora**: `main` = producción, protegida (solo por PR con CI
   verde). Staging se agrega cuando haya operación real y un cambio que lo justifique (~3,5 GB más de
   RAM en el mismo VPS).
4. **Backups de Postgres**: un contenedor `backup` en el mismo compose
   (`eeshugerman/postgres-backup-s3`) hace `pg_dump` diario **cifrado** y lo sube a un bucket S3
   compatible fuera del VPS (Cloudflare R2: capa gratuita de 10 GB), con 14 días de retención; más los
   snapshots del proveedor del VPS. (Los backups programados propios de Coolify aplican a sus recursos
   "Database", no a un Postgres dentro de un compose.)
5. **Vuelta atrás:** `TINKU_TAG=<hash anterior>` en Coolify y redeploy. Con una migración de Flyway no
   retrocompatible, restaurar el backup previo al deploy (T13 TD1).
6. Matching se instala con **PyTorch solo CPU** (T13 A1); la caché del modelo va a un volumen.

## Consecuencias

- Costo: el VPS existente; GHCR y los runners de GitHub, gratis para este volumen. Sin Vercel (su plan
  Hobby no admite uso comercial) ni Supabase.
- Servidor hogareño: un corte de luz o de internet de la casa deja a Tinku fuera de línea mientras
  dure (Cloudflare muestra un error 1033/502). Mitigación recomendada: UPS y un aviso de caída
  (p. ej. un monitor externo gratuito sobre `https://api.tinku.site/api/usuarios/me` esperando 403).
- Todo queda en una máquina: si el VPS cae, cae todo. Mitigación: backups fuera del VPS (R2) y
  restauración ensayada (runbook, paso de ensayo). Es el riesgo que T13 quería evitar; se acepta por
  simplicidad operativa para el piloto y se revisa si crece la operación.
- Presupuesto de memoria (8 GB): Coolify ~1 GB, db 1 GB, matching 3 GB, backend 1,5 GB, frontend
  512 MB (límites en el compose). Margen ~1 GB.
- El frontend hornea `NEXT_PUBLIC_API_URL`/`NEXT_PUBLIC_SITE_URL` en el build (variables `API_URL` y
  `SITE_URL` del repo; default `https://api.tinku.site` / `https://tinku.site`).
- Runbook: `docs/operacion/RUNBOOK_produccion.md`.
