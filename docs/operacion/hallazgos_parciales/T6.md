# T6 — Anónimo / adversarial — hallazgos (producción, tinku.site / api.tinku.site)

Fecha: 2026-10-14. Alcance: `docs/operacion/PLAN_pruebas_produccion.md` §2, §3, fila T6.
Herramienta: `curl` directo contra la API (no scanner automático). Cuentas usadas: solo seed
(`40000001`, `40000002`, `30111222`, `30222333`, `40000012`, `50000001`), DNI inexistente
`99999999` para pruebas de enumeración/rate-limit. Nada destructivo, nada contra el admin real
(`99900301/302`), ninguna ráfaga mayor a 25 requests contra login/recuperar-password.

Leído antes de probar: `SecurityConfig.java`, `JwtAuthenticationFilter.java`, `JwtUtil.java`,
`RateLimitFilter.java`, y los `*Controller.java` de los 9 módulos (156 endpoints relevados).

## Resumen

**No se encontró ninguna fuga de datos entre cuentas (acceso horizontal), ni bypass de rol, ni
bypass de autenticación.** El sistema se comportó de forma defensiva en todos los vectores
probados. No hay hallazgos bloqueantes ni de severidad alta. Hay 2 hallazgos de severidad baja
(cabeceras ausentes) y 1 de severidad baja/informativa (código de estado no estándar en
path-variable inválido). Ver detalle abajo y "No probado y por qué" al final.

## "No probado y por qué"

- **Fuerza bruta real de contraseña / password spraying**: fuera de alcance por regla explícita
  de la tarea (ráfaga mínima, ≤30 requests, y ya alcanzada con las pruebas de rate-limit de
  login). No se intentó adivinar contraseñas de cuentas reales.
- **Registro de usuario real / OCR de DNI**: requiere subir la foto de un DNI real; no se hizo
  (regla del plan, sección 1: "requiere DNI real").
- **Enumeración de usuarios vía `/api/usuarios/verificar-dni` y `/api/tutores/verificar-dni`**:
  no se ejecutó para no consumir presupuesto de rate-limit del grupo `verificar-dni` (límite 5/min
  según `SecurityConfig`) contra cuentas que no son mías; análisis de código (`UsuarioController`,
  `TutorController`) no mostró diferencia de mensaje aparente, pero no se verificó empíricamente.
  **Recomendado para una sesión de prueba dedicada**, de bajo riesgo.
- **Descarga cruzada de archivos binarios** (foto de perfil de Tutor vía `/api/tutores/{id}/foto`,
  credencial vía `/api/tutores/me/credencial`, evidencia/clip de alerta vía rutas admin): se
  verificó que requieren JWT y que las rutas admin están cerradas a no-admin, pero no se intentó
  pedir el archivo binario de OTRO Tutor con el propio id sustituido en `/api/tutores/{idAjeno}/foto`
  porque esa ruta es pública por diseño (foto de perfil visible en el marketplace) — no es un
  vector de acceso horizontal real, se dejó de lado tras confirmar por código
  (`TutorController.foto`) que no expone nada sensible (solo la foto de perfil pública).
- **WebSocket / LiveKit (aula en vivo)**: fuera del alcance de T6 (lo cubre el apartado "Aula en
  vivo" del plan, con dos contextos de browser, no por T6).
- **`X-Forwarded-For` / IP spoofing del rate limiter**: el código (`RateLimitFilter`) usa
  `remoteAddr` salvo que se configure `tinku.rate-limit.header-ip-cliente` (p.ej.
  `CF-Connecting-IP` detrás de Cloudflare); no se pudo verificar desde afuera cuál es la IP que ve
  el proceso Java ni si el header configurado es realmente `CF-Connecting-IP` fiable — queda como
  punto de **confianza en la configuración de Coolify/Cloudflare**, no verificable con pruebas de
  caja negra sin acceso a esa config. Lectura de código: la decisión está documentada y es
  consciente (ADR-000-07 referenciado en el comentario).
- **Escaneo exhaustivo de rutas de Next.js (`/aula/**`, `/buscar`, `/pagar`, `/reservar`, etc.)
  sin sesión**: se probó solo `/admin` como muestra representativa (redirect correcto a login).
  No se iteraron las ~10 rutas restantes del front una por una porque todas comparten el mismo
  middleware de Next (no hay motivo para esperar comportamiento distinto), y el plan prioriza la
  API. Si se quiere, es una extensión barata para una próxima pasada.
- **SQL injection / payloads adversariales en campos de texto** (bio, motivo de denuncia, notas):
  no se probó inyección activa; es un vector de prueba distinto (fuzzing de inputs) que el plan no
  pide explícitamente para T6 y que tocaría escribir datos reales en el seed — se dejó fuera para
  no generar ruido en los datos que usan los demás testers (T1–T5) en paralelo.

## Nota de alcance

Se revisó el `SecurityConfig.java` completo: el único filtro de rate limit corre **antes** de la
autenticación y solo cubre endpoints públicos (`verificar-dni`, públicos de registro/login/
recuperar/resetear, y webhooks) — no hay rate limit en endpoints autenticados, lo cual es
consistente con el diseño (un atacante autenticado ya pasó el costo de tener una cuenta del seed;
igual se evaluó que ningún endpoint autenticado permite acceso cruzado, ver tabla arriba).

## Recomendación (no bloqueante)

Agregar `Content-Security-Policy` en `tinku.site` (front) y, si es fácil vía la config existente
de Cloudflare/el proxy, `Strict-Transport-Security` también en `api.tinku.site` — hoy la API
corre sin HSTS propio (aunque `tinku.site` sí la tiene, y los navegadores no llaman directo a la
API sin pasar antes por el front en el flujo normal, así que el riesgo real es bajo). Severidad
baja, no bloqueante.
